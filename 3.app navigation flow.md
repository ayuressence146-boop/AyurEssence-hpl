App Navigation Flow Logic
1. App Entry Point

The application starts from a single entry point and determines the user's authentication and role before loading the appropriate application flow.

APP LAUNCH
    ↓
Splash / Loading
    ↓
Check Authentication
    ├── Not Authenticated
    │       ↓
    │   Login / Register
    │
    └── Authenticated
            ↓
        Check User Role
            ├── Doctor
            │      ↓
            │   Doctor Dashboard
            │
            ├── Student
            │      ↓
            │   Student Dashboard
            │
            └── Patient
                   ↓
                Patient Dashboard
Entry Rules
Unauthenticated users can access Login and Registration.
Authenticated users are redirected according to their assigned role.
Users cannot manually navigate to another role's dashboard.
Session/token validity is checked before accessing protected screens.
If the session expires, the user is redirected to Login.
Invalid or inactive accounts are denied access to protected resources.

16. Edge Cases
Authentication
Invalid credentials
    → Show login error

Expired session
    → Clear session
    → Redirect to Login

Inactive account
    → Deny access
    → Show account status message

Unauthorized role
    → Redirect to Access Denied
Patient
Patient does not exist
    → Show "Patient not found"

Patient already exists
    → Prevent unintended duplicate creation / require confirmation

Unauthorized patient access
    → Deny access

Patient has no assessments
    → Show empty timeline state
Assessment
Missing patient
    → Assessment creation blocked

Invalid questionnaire
    → Assessment creation blocked

Required question unanswered
    → Submission blocked
    → Highlight incomplete questions

Invalid response
    → Reject response

Assessment already finalized
    → Block modification

Assessment not accessible to user
    → Return authorization error
Calculation
Incomplete assessment
    → Calculation blocked

Invalid scoring configuration
    → Calculation blocked
    → Log error

Calculation failure
    → Do not create invalid result
    → Return retry/error response

No valid result
    → Do not finalize assessment
Recommendation
Assessment not eligible
    → Recommendation draft blocked

Recommendation not approved
    → Patient cannot view it

Non-doctor attempts approval
    → Access denied

Approved recommendation modified
    → Require new review/approval state
Report
Assessment not finalized
    → Final report generation blocked

Unauthorized report access
    → Access denied

Expired share token
    → Shared report unavailable

Invalid share token
    → Access denied

Revoked/cancelled share
    → Shared report unavailable
Follow-up
Invalid patient
    → Reminder creation blocked

Unauthorized reminder modification
    → Access denied

Cancelled reminder
    → No reminder delivery

Completed follow-up
    → Create new assessment when required
    → Update patient timeline
Student Module
Student attempts finalization
    → Access denied

Student attempts recommendation approval
    → Access denied

Assessment not reviewed by doctor
    → Comparison/feedback state remains pending

No mentor feedback
    → Show empty feedback state
17. Global Navigation Rules
Authentication is required for all protected application screens.
Navigation is role-based.
Users can only access resources permitted by their role and ownership/assignment rules.
Doctor is the final authority for assessment finalization.
Student activity is reviewable by the Doctor.
Patient-facing recommendations must be explicitly Doctor-approved.
Finalized assessments are read-only.
Patients can only access their own records.
Shared reports use temporary controlled access.
Failed API requests must not leave the application in an inconsistent state.
Navigation should preserve assessment progress where supported.
Sensitive patient information must not be exposed through unauthorized routes.
Backend authorization remains the source of truth; frontend navigation guards are not a substitute for backend authorization.
Any unauthorized direct API or route attempt must be rejected even if the user manually changes the URL.
